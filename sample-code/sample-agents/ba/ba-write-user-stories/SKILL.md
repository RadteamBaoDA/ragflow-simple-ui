# Write User Stories

## Purpose

Produce implementation-ready user stories without prescribing unnecessary design.

## Task responsibility

Own business analysis, requirement quality, and traceability. Do not make unapproved scope, architecture, implementation, test-pass, or commercial decisions.

## Reference routing

Classify the subtype before detailed work. Read only the matching reference; combine references only when the request spans multiple observable subtypes.

- Read [Feature story](references/feature-story.md) when a user-visible capability is planned.
- Read [Enabler story](references/enabler-story.md) when technical or architectural work enables later business value.
- Read [Defect story](references/defect-story.md) when observed behavior differs from an approved expectation.

## Core method

1. Resolve **Story Statement** using task evidence, applicable constraints, alternatives, and explicit acceptance criteria.
2. Define **Business Context** precisely, including exclusions, owners, interfaces, and assumptions.
3. Derive **Acceptance Criteria** from explicit criteria; state conditions, dissent, and decision authority.
4. Specify **Rules and Constraints** as measurable, traceable, unambiguous statements with accountable ownership.
5. Resolve **Dependencies** using task evidence, applicable constraints, alternatives, and explicit acceptance criteria.
6. Resolve **Trace Links** using task evidence, applicable constraints, alternatives, and explicit acceptance criteria.
7. Reconcile contradictions and state unresolved evidence, decision, and ownership gaps.

## Quality checks

- Tie each conclusion to a named stakeholder, source artifact, business rule, or labeled assumption.
- Keep business need, proposed scope, approved baseline, and technical design distinct.
- Confirm proposed changes are separated from approved baseline content.
- Confirm acceptance, approval, test, release, and customer decisions are claimed only with evidence.
