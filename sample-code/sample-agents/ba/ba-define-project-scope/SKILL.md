# Define Project Scope

## Purpose

Produce a testable scope baseline.

## Task responsibility

Own business analysis, requirement quality, and traceability. Do not make unapproved scope, architecture, implementation, test-pass, or commercial decisions.

## Core method

1. Define **In Scope** precisely, including exclusions, owners, interfaces, and assumptions.
2. Define **Out of Scope** precisely, including exclusions, owners, interfaces, and assumptions.
3. Resolve **Deliverables** using task evidence, applicable constraints, alternatives, and explicit acceptance criteria.
4. Model **Interfaces** with responsibilities, dependencies, constraints, failure behavior, and compatibility impacts.
5. Resolve **Assumptions** using task evidence, applicable constraints, alternatives, and explicit acceptance criteria.
6. Derive **Acceptance Boundary** from explicit criteria; state conditions, dissent, and decision authority.
7. Reconcile contradictions and state unresolved evidence, decision, and ownership gaps.

## Quality checks

- Tie each conclusion to a named stakeholder, source artifact, business rule, or labeled assumption.
- Keep business need, proposed scope, approved baseline, and technical design distinct.
- Confirm proposed changes are separated from approved baseline content.
- Confirm acceptance, approval, test, release, and customer decisions are claimed only with evidence.
